# Standalone application architecture

Moirasia is a controller plus a feature host. As a controller, its main process talks to a small AppKit agent that discovers, opens, focuses, and gracefully quits the standalone Amove, Vox, Exithibition, Bonded, and Orbis bundles. As a host, it can run a product inside the suite process when the product ships a feature package.

Feature code lives in each product's own repository under `apps/integrated/` (Amove, Exithibition, Bonded, and Orbis) and implements the `MoirasiaFeature` contract from `@moirasia/desktop-shell/feature`: `register(ctx)` brings the product runtime up, `dispose()` tears it down completely, and `activate()` selects/focuses its primary surface. The host owns the discriminated `FeatureContext`, named resource maps, and the `EmbeddedFeatureSurface` supplied by `EmbeddedFeatureHost`. Each feature calls `acquireFeatureSurface` from `@moirasia/desktop-shell/feature-surface-host`. In suite mode it returns the shell surface without creating or controlling a window. In standalone mode it creates and owns the feature's primary `BrowserWindow`, then handles validation, guards, appearance, renderer loading, activation, and teardown. Utility windows such as Amove's Shelf remain feature-owned in either host.

Feature backends register at suite startup, while primary panel JavaScript is lazy in the shell renderer. `FeatureRuntime` (`src/main/features/runtime.ts`) resolves each installed backend through a string-literal `import()`, so rollup code-splits the backend and an uninstalled feature's code is never evaluated; the suite context join lives beside it in `src/main/features/suite-context.ts`. React panel chunks load on first tab visit and stay mounted while the feature remains installed. Availability is a persisted boolean per product in the v3 shell settings, layered above the product's own settings so uninstalling loses nothing. Uninstall mid-session clears the active tab before `dispose()`; the code chunk stays in memory until relaunch, which the hub reports with a restart banner. Install mid-session registers the feature right away.

The feature catalog (`packages/desktop-shell/src/feature-catalog.ts`, re-exported by `@moirasia/desktop-shell/feature`) is the single owner of the shared facts about the four embedded features: identity, labels, bundle and executable names, descriptions, display groups, icon keys, menu order, per-host-mode resource requirements, and artifact facts — every binary, worker, and asset bundle a feature ships, its filename (or napi base name plus the platform `.node` matrix in `nativeAddonFileName`), the app-repo build layout it comes from, where staging places it, where packaged resources land in the suite and in the app's own bundle, and which source the suite trusts in development (`suiteDevSource`). Hosts resolve these facts against their own roots through `artifactPath`; the catalog never resolves paths itself. The application catalog (`packages/desktop-shell/src/application-catalog.ts`, re-exported by `@moirasia/desktop-shell`) owns the same identity facts for the five standalone applications the controller launches — including Vox, which is no longer embedded — and feeds the Applications menu, its Command+1..5 accelerators, and the `ApplicationId`/`ControllerPage` guards. Every caller derives what it needs from these catalogs — controller snapshots, the Features page copy and groups, appearance product order, and the default resource requirements checked by `validateFeatureResources`. The catalogs are pure data: they import nothing, never touch the filesystem, and never resolve host-owned paths — loading backends, rendering panels, driving preload bridge exposure, and the preload/renderer page maps stay explicit in each host (literal dynamic imports, literal panel adapters, hand-written `contextBridge` calls, `FeatureContext` resource maps). Adding an embedded feature or a controlled application starts with one catalog entry; the remaining edits are deliberate host adapters.

Artifact facts are resolved, not restated. Suite packaging (`electron-builder.yml`) and the staging script (`scripts/stage-feature-binaries.mjs`) stay hand-written — the builder config is YAML and the script carries bespoke per-app build commands — but both are contract-pinned against the catalog by `tests/feature-artifacts.test.ts`, together with the four app-owned builder configs and the root `package.json` worker outDir. Every artifact follows one rule: the script stages it under `native/staged/features/<id>/<dir>`, the suite packages it at `Resources/features/<id>/<dir>`, and the app's own bundle keeps its own destination recorded as `standaloneResource` (for Exithibition and Bonded, `Resources/native/<file>`; the suite's copy moved to the namespaced `features/exithibition/native` when staging was normalized). In suite development the catalog records which source each feature trusts: Amove, Exithibition, and Bonded read the app repo's own build output, while Orbis reads the staged copies that `features:worker` and `features:native` place in `predev`. Hosts still compose the directory inline (packaged `process.resourcesPath`, dev `app.getAppPath()` or the app's own dev root) and join it with the artifact through `artifactPath`.

The shell sidebar groups General and Features under Essentials. The Features page manages every supported embedded product, including disabled or failed-to-load products. The Apps group links only installed backends that loaded successfully, so it never selects an unusable panel. Standalone bundles remain available through the macOS Applications menu and its keyboard shortcuts rather than through a renderer page.

Every feature must keep building as its own standalone app. The standalone launcher (`runStandaloneLaunch`, `@moirasia/desktop-shell/main`) owns the standalone launch sequence: the login-item control branch, the single-instance lock, ready-time registration, activation re-focus, quit policy, and awaited teardown. Entry files keep only app facts — identity, platform scope, the `userData` override env, the menu template, the CSP policy, failure-dialog copy, and Amove's quit predicate. The control check precedes the platform guard and the lock, so a control command always answers. Product behavior still lives in each app repository; the suite host is untouched.

Vox is not an embedded feature. Its repository lives at `apps/standalone/Vox`, keeps the `com.moirasia.vox` identity, its own dashboard, tray, overlay, login-item control, and Bun workflow, and no longer implements the `MoirasiaFeature` contract. Moirasia controls Vox only through the application catalog: the Applications menu and Command+2 launch or focus the standalone bundle, and the shell exposes no Vox panel, staging, or feature runtime entry.

The shared desktop shell supplies consistent primary-window chrome and appearance for Moirasia, Amove, Vox, Exithibition, Bonded, and Orbis. `DesktopAppShell` owns the full primary `BrowserWindow` viewport and is the only owner of the neutral 36px product bar and its compact sun/moon appearance toggle. The product bar never scrolls with app content. `DesktopNavigation` supports flat and labeled-group layouts and changes from a 220px sidebar to a horizontal row below 720px. `DesktopPage`, `ScrollArea`, and app-level containers decide how their content scrolls. The shell's `DesktopPage` owns the unified page margin — 24px vertical / 30px horizontal, tightening to 20px below 980px and 16px below 650px — and apps must not declare their own page-level padding; utility surfaces (Amove's Shelf, Vox's overlay) remain intentionally excluded. `DesktopContentHeader` remains ordinary app content below the draggable product bar, so the shell does not pin it while its page scrolls. Embedded panels render content only, leaving the outer Moirasia shell as the sole owner of the product bar and appearance control in suite mode. The feature catalog owns standalone window geometry, fullscreen support, and navigation policy. The feature surface host resolves those facts when it creates the window. Utility surfaces are intentionally excluded: Amove's shelf retains its compact borderless window and Vox's dictation overlay remains transparent, floating, and non-activating.

Login-item changes are executed by the target bundle through the versioned `--moirasia-control` protocol because macOS login services are scoped to the calling bundle. The command uses isolated Chromium data and exits after one JSON response.

Vox is a standalone-only application. While stale pre-move Moirasia builds that still embed Vox may exist, Vox contends for a per-user lease before it starts any window, IPC, database, or VoxNative process; the lease is a transitional guard and is scheduled for removal once stale builds are gone. Vox always owns its dashboard, tray, transparent overlay, Dock behavior, login-item control, bundle identity, and the Command+2 launch path.

On first standalone launch after leaving the suite, Vox reverse-migrates the suite's data. It snapshots the suite store at `Application Support/Moirasia/features/vox/vox.sqlite` through SQLite itself, then merges it into `Application Support/Vox/vox.sqlite`: entity rows union by id with the suite row winning the rare collision (ids are random UUIDs), parents before children so foreign keys stay satisfied, daily aggregate counters taking the per-day maximum, and settings resolving per key in the suite's favor except launch-at-login, which the standalone store keeps and re-applies to its login item. The standalone store is backed up to `vox.pre-merge-backup.sqlite` before any write, the merge runs in one transaction that rolls back on failure, and the outcome is recorded in a `.vox-suite-merge-v1.json` marker that lets a failed merge retry and keeps every terminal outcome from running twice. On success the suite directory is removed. A suite store with a different schema leaves both stores untouched and reports the mismatch instead of guessing.

Both hosts intentionally share downloaded models in `Application Support/Vox/Models` and provider credentials in the `com.moirasia.vox.providers` Keychain service. Vox owns its own macOS permission grants under its own bundle identity. Packaged native resources live at `Resources/native` for Vox.

Bonded is the third embedded feature. Its controller receives its data directory and firewall-helper path from the host. Standalone settings stay under Bonded's `userData`; suite settings live under Moirasia's `features/bonded` directory. A pristine suite store imports the first valid standalone primary or backup document once, without changing the source. The two stores then diverge. A per-user runtime lease under `Application Support/Moirasia` prevents standalone Bonded and the embedded feature from controlling the global monitor and PF session together. The suite packages its helper at `Resources/features/bonded/native/BondedFirewallHelper`; standalone Bonded uses `Resources/native/BondedFirewallHelper`. Both require administrator approval when the helper is installed.

Orbis is the fifth controlled standalone application and another embedded feature. `apps/integrated/Orbis/src` owns its scanner, worker protocol, temporary `node:sqlite` index, context-isolated preload bridge, and SVG renderer. `apps/integrated/Orbis/src/main/index.ts` keeps only the standalone identity, menus, CSP, login-item control, and quit policy. The app builds one ESM worker at `scan-worker.mjs` via `scripts/build-worker.mjs`; Moirasia stages it at `native/staged/features/orbis/worker`, while standalone development stages it at `apps/integrated/Orbis/worker-dist`. Packaged builds place it at `Resources/features/orbis/worker/scan-worker.mjs`. `ORBIS_SCAN_ROOT` supplies a fixture root for automated scans, so tests never need to traverse the real startup volume. Full Disk Access belongs to Moirasia in suite mode and to the Orbis bundle in standalone mode.
